# [초안] IACS UR E26/E27 대응 체크리스트: 계약부터 인도까지 단계별 준비물

> 검토용 초안입니다. 게시 전 대표 검토가 필요합니다.
> - 예정 slug: `iacs-ur-e26-e27-checklist`
> - 카테고리: Compliance
> - 설명(검색 결과용): 신조선 계약부터 인도까지, IACS UR E26/E27 선급 심사에서 요구되는 문서와 시험을 단계별 체크리스트로 정리했습니다. 조선소 · 선주 · 기자재 공급사가 각자 준비할 항목을 구분했습니다.
> - 기존 글 [IACS UR E26/E27 규제 개요와 대응 전략]과의 관계: 개요 글이 "무엇을 요구하는가"를 다뤘다면, 이 글은 "언제 무엇을 제출하는가"를 다룹니다.
> - 확인 요청: ⚠️ 표시한 부분은 실제 수행 경험 기준으로 맞는지 봐 주십시오.

## 체크리스트가 필요한 이유

UR E26/E27은 2024년 7월 1일 이후 건조 계약 선박에 적용됩니다. 요구사항 자체는 개요 글에서 정리했지만, 현장에서 막히는 지점은 다른 데 있습니다. "어느 단계에서 어떤 문서를 누가 내야 하는가"가 계약서에 분명히 적혀 있지 않으면, 승인도면 단계에서 기자재 공급사의 자료를 기다리다 일정이 밀리고, 시운전 직전에 시험 절차서를 급히 만드는 일이 생깁니다.

이 글은 신조선 프로젝트의 흐름을 다섯 단계로 나누고, 단계마다 조선소 · 선주 · 기자재 공급사가 준비할 항목을 적었습니다. 선급마다 서식과 명칭이 조금씩 다르지만, 통합규칙이 요구하는 문서의 뼈대는 같습니다.

## 먼저 정할 것: 적용 범위와 책임

| 항목 | 내용 | 주체 |
|---|---|---|
| 적용 여부 | 건조 계약일이 2024년 7월 1일 이후인지 확인. 계약일 기준이며 기공일이나 인도일이 아닙니다 | 선주 · 조선소 |
| 대상 CBS 범위 | UR E22의 시스템 카테고리(I · II · III) 기준으로 E26 대상 CBS(Computer Based System) 목록 확정. 추진 · 조타 · 발전 · 화재 탐지 · 빌지/밸러스트 · 항해 · 통신 등 E26이 명시한 기능은 필수 포함 | 조선소 |
| 책임 분담 | 선박 수준 문서(E26)는 조선소, 시스템 수준 증빙(E27)은 공급사, 운항 단계 유지는 선주. 이 분담을 건조 계약과 기자재 구매 사양서에 명기 | 선주 · 조선소 |
| 선급 협의 | 적용 선급의 E26/E27 가이드라인(선급별 Rule · Guidance 번호) 확인, 심사 일정과 제출 서식 사전 협의 | 조선소 |

⚠️ 계약 단계에서 가장 자주 빠지는 것은 기자재 구매 사양서의 E27 조항입니다. 공급사가 "E27 대응 가능"이라고만 답하면 부족하고, 어떤 증빙(아래 3단계 표)을 언제 제출하는지까지 사양서에 들어가야 합니다.

## 1단계. 설계 · 승인도면: 선박 수준 문서

조선소가 선급에 제출하는 E26 핵심 문서입니다. 승인도면 일정에 맞춰 준비합니다.

- [ ] **선박 자산 목록(Vessel Asset Inventory)** — 대상 CBS 전체와 각 시스템의 하드웨어 · 소프트웨어 · 네트워크 인터페이스. 공급사 자료가 모이기 전에는 초안으로 제출하고 FAT 전까지 확정
- [ ] **구역 및 통로 설계(Zones and Conduits Diagram)** — IEC 62443의 보안 구역 개념으로 선내 네트워크를 나누고 구역 간 통로를 정의. 어떤 CBS가 어느 구역에 속하는지, 구역 간 통신은 무엇으로 통제하는지
- [ ] **사이버 보안 설계 설명서(Cyber Security Design Description)** — 네트워크 보호 · 접근 통제 · 악성코드 방어 · 원격 접속 · 무선 통신 · 이동식 매체 처리 방식을 설계 기준으로 설명
- [ ] **선박 사이버 복원력 시험 절차서(Ship Cyber Resilience Test Procedure)** — 인도 전 시험에서 무엇을 어떻게 확인할지. 승인도면 단계에서 초안, 시운전 전 확정
- [ ] **위험 평가(Risk Assessment)** — 대상 CBS와 통로별 위협과 영향, 완화 조치. 구역 설계의 근거 자료

⚠️ 실무에서는 "자산 목록"과 "구역 설계"를 한 번에 확정하려다 지연되는 경우가 많습니다. 자산 목록은 살아 있는 문서로 두고, 공급사 자료가 도착할 때마다 갱신하는 운영 방식이 심사에도 유리했는지 확인해 주십시오.

## 2단계. 기자재 발주: 공급사에 요구할 것

E27은 개별 CBS의 보안 역량을 다룹니다. 조선소가 공급사에 요구하고, 공급사가 증빙을 냅니다.

- [ ] **보안 역량 문서(Security Capabilities Document)** — E27이 정한 기본 보안 역량(UR E27 Rev.1 기준 30개 항목)에 대해 시스템이 어떻게 충족하는지 항목별로 기술
- [ ] **추가 보안 역량 적용 여부** — 선주 요구나 구역 설계에 따라 적용되는 추가 역량(11개 항목)의 적용 범위를 조선소 · 선주와 합의
- [ ] **보안 개발 수명주기 증빙** — 공급사의 개발 · 시험 · 취약점 처리 절차. IEC 62443-4-1 수준의 절차 문서나 선급 인증서
- [ ] **인터페이스 정의서** — 다른 CBS 및 외부와 연결되는 모든 물리 · 논리 인터페이스, 사용 프로토콜과 포트
- [ ] **소프트웨어 구성 목록** — 운영체제 · 미들웨어 · 애플리케이션 버전, 알려진 취약점 관리 방식
- [ ] **형식 승인(Type Approval) 또는 선급 평가 결과** — 선급 TA가 있으면 개별 심사가 크게 줄어듭니다. 없으면 선박 단위로 선급 평가를 받아야 하므로 일정에 반영

⚠️ "TA 보유"라고 답하는 공급사도 적용 선급과 규칙 개정판(Rev.0 · Rev.1)이 다른 경우가 있습니다. 발주 전에 TA 증서의 선급 · 규칙 버전 · 적용 제품 모델을 확인하는 절차가 실제로 필요했는지 봐 주십시오.

## 3단계. FAT: 공급사 공장에서 확인할 것

- [ ] 보안 역량 문서의 항목별 시험 결과(공급사 자체 시험 보고서)
- [ ] 기본 계정 · 기본 비밀번호 제거, 불필요한 서비스 · 포트 폐쇄 상태 확인
- [ ] 로그 기록 · 시간 동기화 · 백업/복원 기능 동작 확인
- [ ] 소프트웨어 업데이트 절차(공급사의 업데이트 서비스)와 무결성 검증 방식 확인
- [ ] 인터페이스 정의서와 실제 구성의 일치 여부 확인

FAT에서 확인한 내용은 선박 사이버 복원력 시험 절차서의 사전 조건으로 연결됩니다. FAT 결과를 시험 절차서 부록으로 정리해 두면 시운전 단계의 중복 시험을 줄일 수 있습니다.

## 4단계. 탑재 · 시운전: 선박 사이버 복원력 시험

- [ ] **시험 절차서 확정** — 승인도면 단계의 초안을 실제 탑재 구성에 맞춰 갱신, 선급 승인
- [ ] **구역 경계 시험** — 구역 간 허용되지 않은 통신이 차단되는지, 방화벽 · 스위치 설정이 설계와 일치하는지
- [ ] **접근 통제 시험** — 계정 · 권한 · 원격 접속 경로가 설계대로 통제되는지
- [ ] **탐지 · 로그 시험** — 이상 이벤트가 기록되고 담당자가 확인할 수 있는지
- [ ] **복구 시험** — 백업에서 복원이 되는지, 복원 후 기능이 정상인지
- [ ] **시험 보고서** — 선급 입회 결과와 미결 사항(Punch list), 조치 계획

⚠️ 시운전 일정에서 사이버 복원력 시험에 배정되는 시간이 실제로 얼마나 필요했는지(예: 선종별 하루 · 이틀) 경험치를 넣으면 글의 설득력이 커집니다. 수치를 주시면 반영하겠습니다.

## 5단계. 인도 · 운항: 선주에게 넘어가는 것

- [ ] **선박 사이버 보안 · 복원력 프로그램 문서** — 운항 중 유지관리 책임, 사고 대응 계획, 복구 계획, 교육 계획
- [ ] **최종 자산 목록과 설계 문서 일체** — 인도 시점 구성 기준. 이후 변경은 선주의 변경 관리 절차로
- [ ] **사고 대응 계획(Incident Response Plan)** — 선내 담당자 · 육상 지원 · 공급사 연락 체계, 격리 · 복구 순서
- [ ] **정기 점검 항목** — 선급 정기 검사 시 확인되는 항목(문서 최신화, 계정 관리, 패치 이력)을 선주 점검표에 반영

운항 단계에서 가장 흔한 문제는 문서는 있는데 실제 구성이 바뀐 경우입니다. 공급사 원격 지원이나 소프트웨어 업데이트가 자산 목록과 구역 설계에 반영되지 않으면, 다음 검사에서 지적 사항이 됩니다.

## 한 장으로 보는 역할별 요약

| 단계 | 조선소 | 선주 | 기자재 공급사 |
|---|---|---|---|
| 계약 | 적용 범위 · 선급 협의, 구매 사양서에 E27 조항 | 책임 분담 명기, 추가 보안 역량 요구 여부 결정 | E27 대응 범위와 증빙 일정 회신 |
| 설계 | 자산 목록 · 구역 설계 · 설계 설명서 · 시험 절차서 초안 · 위험 평가 | 설계 검토, 운항 요구사항 전달 | 보안 역량 문서 · 인터페이스 정의서 · 소프트웨어 목록 |
| FAT | 입회, 결과를 시험 절차서에 연결 | (필요 시) 입회 | 자체 시험 보고서, 강화 설정 상태 시연 |
| 시운전 | 복원력 시험 수행, 보고서 | 입회, 미결 사항 확인 | 시험 지원, 미결 조치 |
| 인도 · 운항 | 최종 문서 일체 인계 | 프로그램 문서 운영, 변경 관리, 정기 검사 대응 | 업데이트 서비스, 취약점 통지 |

## 맺음말

E26/E27 대응은 문서를 많이 만드는 일이 아니라, 설계 단계의 결정이 시험과 운항까지 일관되게 이어지도록 관리하는 일입니다. 계약서에 역할을 적고, 자산 목록을 살아 있는 문서로 유지하고, FAT 결과를 시운전 시험에 연결하면 심사 지적의 대부분을 미리 막을 수 있습니다.

광명마리타임은 설계 단계의 구역 설계부터 선급 입회 시험까지, 조선소와 공급사가 각 단계에서 제출할 자료를 함께 준비합니다.
